ELobbyCheckErrCode UTeamLobbyManager::SCheckArenaCondition()  
{  
    if (!pWorld.IsValid() || pWorld->IsPendingKill())  
    {       
	    UE_LOG(LogTemp, Warning, TEXT("GetWorld failed"));  
       return ELobbyCheckErrCode::ELCEC_Unknown;  
    }    
    
    int32 PlayerNumberMin = 0, PlayerNumberMax = 0;  
    auto ArenaType = LobbyInfo.kv_data.Contains("ArenaGameType") ? LobbyInfo.kv_data["ArenaGameType"] : TEXT("");  
    
    if (LobbyInfo.LobbyTypes == ELobbyTypes::ELT_PVEMatch 
	    && FCString::Atoi(*ArenaType) == EArena_PVE_Survival)  
    {       
	    if (auto Found = UTableManager.FindTableRow<FArenaTypeTableRow>(FName("PVE_Survival")))  
       {          
	       PlayerNumberMin = Found->MinPlayerNum;  
           PlayerNumberMax = Found->TeamNum;  
       }  
       if (!IsLobbyPveAvailableSelf(pWorld.Get(), LobbyInfo))  
       {          
	       return ELobbyCheckErrCode::ELCEC_PVEUnLock;  
       }

       if (ELobbyCheckErrCode::ELCEC_Success != CheckErrCode)  
       {          
	       return CheckErrCode;  
       }    
    }    
    return ELobbyCheckErrCode::ELCEC_Success;  
}

### 介绍下UPVPLobbyManagerPGOS::CreateLobby这个函数是干什么的            
● CreateLobby 有两个重载：

  第一个重载 (line 389) — 只是一个简单转发：
  bool UPVPLobbyManagerPGOS::CreateLobby(ELobbyTypes LobbyTypes, const FCreateLobbyUserParams& UserParams)
  {
      return CreateLobby(LobbyTypes, UserParams, nullptr);
  }
  把参数转发给三参数版本，RetFunc 传空。

  第二个重载 (line 2231) — 真正的实现，做以下几件事：

  1. 前置检查 — 确认当前不在处理中(bProcessing)、已登录成功、尚未加入/创建房间、玩家数据同步完成
  2. 获取 PGOS SDK 的 Lobby API 指针
  3. 根据房间类型选择配置 — 根据 ELobbyTypes（抢劫/PVP/队伍/RGM/FFA/匹配等）选择不同的 PGOS lobby_config（PGOS_CustomConfig 或 PGOS_MultiModeCfg 等）
  4. 生成房间 ID 和搜索标签 — 调用 GenerateLobbyIdAndFillSearchTags
  5. 合法性检查 — 调用 SCheckConditionLegal 验证玩家是否有资格创建该类型房间，不合法则设置失败状态并弹出 Toast 提示
  6. 调用 PGOS SDK 的 CreateLobby API — 设置好参数后异步调用，回调统一走 CreateLobbyCallback，如果有传入 RetFunc 也会额外回调
  7. 更新状态 — 设置 CurrentStatus = EPLS_Creating、bProcessing = true

  简而言之，这个函数是"创建 PGOS 房间"的入口，负责参数组装、合法性校验、调用 SDK 创建，结果通过回调异步通知。

### 本项目里的Mission是个什么概念？ 是一般游戏中所说的任务系统吗？                                                                                                                                                                    
● 在这个项目里，Mission 不是一般意义上的"任务/ quest 系统"，而更接近 "副本/关卡" 的概念。它代表一段可独立加载的玩法实例，对应一张副本地图里完整的一局游戏。

  从代码可以看到几种 Mission 类型：
                                                                            
  │ FStoryMissionDungeon │ 主线剧情副本 │ 剧情推图关卡           │
  │ FHeistMultiInstance  │ 合作抢劫副本 │ 合抢/小岛抢劫的 PVE 局 │
  │ FContactMission      │ 联系人任务   │ NPC 给的副本任务       │
  │ FVehicleMission      │ 载具任务     │ 载具玩法关卡           │

  核心结构 FMissionData 的关键字段：
  - MissionType — 区分是哪类副本（主线/合抢/联系人等）
  - TargetStreamingLevelPath — 要加载的关卡流式 level（即实际地图）
  - MissionClass — 处理该副本逻辑的 ABaseMission 子类
  - NumberOfPlayers — 允许的玩家数
  - RequirementsCond — 玩家进入条件（等级、功能锁等）

● 在这个项目里，Mission 不是一般意义上的"任务/ quest 系统"，而更接近 "副本/关卡" 的概念。它代表一段可独立加载的玩法实例，对应一张副本地图里完整的一局游戏。

  从代码可以看到几种 Mission 类型：

  │ FStoryMissionDungeon │ 主线剧情副本 │ 剧情推图关卡           │
  │ FHeistMultiInstance  │ 合作抢劫副本 │ 合抢/小岛抢劫的 PVE 局 │
  │ FContactMission      │ 联系人任务   │ NPC 给的副本任务       │
  │ FVehicleMission      │ 载具任务     │ 载具玩法关卡           │

  核心结构 FMissionData 的关键字段：
  - MissionType — 区分是哪类副本（主线/合抢/联系人等）
  - TargetStreamingLevelPath — 要加载的关卡流式 level（即实际地图）
  - MissionClass — 处理该副本逻辑的 ABaseMission 子类
  - NumberOfPlayers — 允许的玩家数
  - RequirementsCond — 玩家进入条件（等级、功能锁等）

  所以当你创建小岛抢劫房间时，MissionId 指向的就是 FHeistMultiInstance 表里的一行，它定义了这张副本用哪个地图、哪些刷怪配置、奖励等。SCheckMissionCondition 做的就是检查这张副本配置是否存在、玩家是否解锁、是否在冷却等。
